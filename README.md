# max-smart-city
# Одна заявка на весь дом

Чат-бот и мини-приложение в MAX для жителей многоквартирных домов и управляющих компаний.
Хакатон MAX 2026, трек «Умный город».

Житель сообщает о проблеме, соседи нажимают «У меня тоже» — управляющая компания получает одну заявку
вместо десятков, с нормативным сроком по закону и ценой каждого часа простоя.

> **Как проверить:** ссылка на бота, сценарий на 5 минут и тестовые данные — в разделе
> [Проверка решения (для жюри)](#проверка-решения-для-жюри).

## Быстрый старт для разработки

### Что нужно установить

| Что | Версия | Как проверить |
|---|---|---|
| Node.js | 22 | `node -v` → `v22.x` |
| pnpm | 12.5.1 (ставится автоматически через corepack) | `pnpm -v` |
| Docker + Docker Compose v2 | любая актуальная | `docker compose version` |
| Git | любая | `git --version` |

**Windows:** работайте внутри WSL 2 (Ubuntu), а не в PowerShell, и держите репозиторий в файловой системе
WSL (`~/projects/...`), не на диске `C:`. Подробная установка — в разделе [Установка на Windows](#установка-на-windows).

### Первый запуск

```bash
git clone git@github.com:MrHold/max-smart-city.git
cd max-smart-city
pnpm install                 # библиотеки по pnpm-lock.yaml
cp .env.example .env         # локальные настройки; .env в git не попадает
docker compose up -d db      # Postgres в фоне
docker compose ps            # у db должно быть (healthy)
pnpm typecheck               # проверка типов во всех пакетах
```

Если всё прошло без ошибок — окружение готово.

### Установка на Windows

1. PowerShell от администратора: `wsl --install -d Ubuntu`, перезагрузка.
2. Docker Desktop → Settings → Resources → WSL integration → включить Ubuntu.
3. В терминале Ubuntu:
   ```bash
   sudo apt update && sudo apt install -y git curl unzip build-essential
   curl -fsSL https://fnm.vercel.app/install | bash
   source ~/.bashrc
   fnm install 22 && fnm default 22
   corepack enable pnpm
   git config --global core.autocrlf input
   ```
4. VS Code: расширение **WSL**; проект открывать командой `code .` из терминала Ubuntu.

## Что где лежит

Монорепозиторий: несколько пакетов в одном репозитории, общие настройки в корне.

```
apps/
  bot/          @msc/bot        чат-бот MAX: команды, наряды исполнителю, уведомления
  api/          @msc/api        HTTP API для мини-приложения, проверка входа по аккаунту MAX
  miniapp/      @msc/miniapp    мини-приложение (React + Vite): экраны жителя, мок MAX Bridge, Dockerfile с Caddy
packages/
  domain/       @msc/domain     ядро: договоры данных, сроки, расчёт перерасчёта, кластеры
  db/           @msc/db         схема БД (Drizzle) и миграции, шифрование идентификаторов MAX
  documents/    @msc/documents  PDF: заявление о перерасчёте, акт                   — будет
regions/        данные регионов: категории, сроки, тарифы, дома                     — будет
rules/federal/  федеральные нормы: ПП 354, ПП 416                                   — будет
```

Бэкенд (бот и API) запускается из TypeScript напрямую через `tsx`, без шага сборки.
`tsc` используется только для проверки типов. Мини-приложение собирается Vite в статические файлы.

Мини-приложение написано на React 19: библиотека `@maxhub/max-ui` требует ровно `react@19.2.8`.
Интерфейс собран своими компонентами по макету команды, из MAX UI используется провайдер платформы и темы.

### Архитектура

```
        MAX (мобильный / веб)
        │                  │
   чат с ботом     мини-приложение
        │                  │
        ▼                  ▼
┌──────────── Caddy (HTTPS) ────────────┐
│ /webhook → bot   /api → api   / → miniapp │
└───────────────────────────────────────┘
        │                  │
   apps/bot           apps/api
        └──────┬───────────┘
      packages/domain · db · documents
               │
          PostgreSQL
```

## Переменные окружения

Шаблон — `.env.example`. Рабочий `.env` создаётся копированием и **никогда не коммитится**.
Новая переменная добавляется в `.env.example` в том же PR, что и код, который её использует.

| Переменная | Для чего | Пример |
|---|---|---|
| `POSTGRES_USER` | пользователь БД | `msc` |
| `POSTGRES_PASSWORD` | пароль БД (в примере — только для локального запуска) | `msc_local_only` |
| `POSTGRES_DB` | имя базы | `msc` |
| `DATABASE_URL` | строка подключения для приложений | `postgres://msc:…@localhost:5432/msc` |
| `BOT_TOKEN` | токен бота MAX (выдают организаторы) | — |
| `BOT_MODE` | `polling` — локально, `webhook` — на сервере | `polling` |
| `API_PORT` | порт HTTP API | `3001` |
| `PHOTOS_DIR` | каталог для фото заявок (в Docker — том) | `./data/photos` |
| `CORS_ORIGIN` | откуда разрешены запросы к API, через запятую; локально — dev-сервер мини-приложения | `http://localhost:5173,http://127.0.0.1:5173` |
| `PUBLIC_DOMAIN` | домен для Caddy; пусто — локально на `:80` без TLS, на сервере — автоматический HTTPS | `example.ru` |
| `VITE_API_URL` | адрес API для мини-приложения; пусто — тот же домен | `http://localhost:3001` |
| `VITE_API_MOCK` | `1` — мини-приложение работает на встроенном моке API, без бэкенда | `1` |
| `VITE_DEMO_MODE` | `1` — показывать демо-часы (сдвиг времени для показа сроков) | `1` |
| `DEMO_MODE` | `1` — сервер разрешает перемотку времени (`/api/demo/clock`) и роль диспетчера одним аккаунтом; на защите включён, в пилоте выключен | `1` |
| `APP_LINK` | ссылка на бота `https://max.ru/<ник>`; из неё API собирает `shareUrl` для «У меня тоже» | `https://max.ru/msc_bot` |
| `VITE_BOT_NAME` | ник бота для встроенного мока API; с настоящим API ссылка приходит с сервера | — |
| `VITE_DEV_INIT_DATA` | подписанная initData для работы мини-приложения в браузере с настоящим API; печатает `pnpm --filter @msc/api sign-init-data` | — |
| `WEBHOOK_SECRET` | секрет, который MAX прикладывает к событиям webhook; `openssl rand -hex 32` | — |
| `USER_HASH_SECRET` | ключ, по которому пользователь MAX находится в базе; **генерируется один раз** | — |
| `USER_ID_ENC_KEY` | ключ шифрования идентификатора MAX (32 байта); **генерируется один раз** | — |
| `INIT_DATA_MAX_AGE_SEC` | сколько секунд действуют данные запуска мини-приложения | `3600` |
| `RATE_LIMIT_MAX` | запросов в минуту на одного пользователя | `120` |
| `DUPLICATE_WINDOW_MIN` | окно, в котором повторная заявка считается дублем, минут | `10` |
| `DOC_LINK_TTL_MIN` | срок жизни подписанной ссылки на PDF, минут | `30` |
| `TEST_DATABASE_URL` | база для тестов API; пусто — такие тесты пропускаются | — |

Переменные `VITE_*` читаются Vite **на этапе сборки** и попадают в статику: менять их на сервере
без пересборки образа нельзя.

Рабочие значения токенов и ключей для проверки передаются жюри на первом слайде презентации,
а не в репозитории. Почему `USER_HASH_SECRET` и `USER_ID_ENC_KEY` нельзя менять и что ставить
на сервере — в [docs/operations.md](docs/operations.md).

### Права на свои данные

| Адрес | Что делает |
|---|---|
| `GET /api/me/data` | что о вас хранится: состав, количество записей и зачем каждая нужна |
| `DELETE /api/me` | удалить привязку к дому, согласия, присоединения и очередь уведомлений |

Заявки при удалении не стираются, а **перестают быть связаны с человеком**: они нужны дому,
управляющей организации и соседям, которые к ним присоединились. У пользователя затираются
хеш и шифротекст идентификатора MAX — после этого строка никому не соответствует,
а следующий вход создаёт нового пользователя.

Ни имя, ни идентификатор MAX в открытом виде в ответе не появляются: мы их не храним.

### Документы по заявке

| Адрес | Когда доступен |
|---|---|
| `GET /api/requests/:id/documents/claim.pdf` | есть посчитанная сумма перерасчёта; ссылка приходит в карточке в `claim.url` |
| `GET /api/requests/:id/documents/gji.pdf` | истёк срок ответа управляющей организации, то есть `gji.available` в карточке стало `true` |

Кнопка в мини-приложении открывает PDF обычным переходом, а браузер не отправляет
`X-Init-Data`, поэтому адрес документа подписывается на ограниченное время:

- `claim.url` в карточке заявки уже содержит подпись — `…/claim.pdf?exp=…&sig=…`, 30 минут;
- `POST /api/requests/:id/documents/claim/link` и `…/gji/link` выдают свежую ссылку
  (для жалобы в ГЖИ и когда прежняя истекла), ответ — `{ url, expiresAt }`;
- сам PDF принимает либо `X-Init-Data`, либо валидную подпись.

Право проверяется при выдаче ссылки, подделанная или просроченная подпись — `403`.
Срок жизни настраивается переменной `DOC_LINK_TTL_MIN`.

Раньше срока API отвечает `409` с объяснением: жалобу в инспекцию, поданную
до истечения срока ответа управляющей организации, возвращают как преждевременную.

Шрифты для PDF берутся из самого pdfmake, отдельных файлов в репозитории нет.

### Docker Desktop не стартует после падения

Если при запуске выпадает «An unexpected error occurred» с текстом про
`rename …sock …stale: The file cannot be accessed by the system` — это файлы сокетов
от прошлого аварийного завершения. Нажать **Quit** (не «Reset to factory defaults»,
она сносит контейнеры и образы) и из WSL выполнить:

```bash
bash scripts/fix-docker-desktop.sh
```

Контейнеры, образы и база при этом не страдают: они внутри виртуальной машины.

### Демо-часы

Ждать два часа, пока истечёт срок и откроется жалоба в ГЖИ, на защите никто не будет,
поэтому при `DEMO_MODE=1` время можно перематывать. Сдвиг лежит в базе одной строкой,
поэтому его видят и API, и бот.

```bash
curl http://localhost:3001/api/demo/clock                      # текущий сдвиг
curl -X POST http://localhost:3001/api/demo/clock \
  -H "X-Init-Data: $INIT_DATA" -H 'Content-Type: application/json' \
  -d '{"shiftHours": 3}'                                       # вперёд на 3 часа
curl -X POST http://localhost:3001/api/demo/clock \
  -H "X-Init-Data: $INIT_DATA" -H 'Content-Type: application/json' \
  -d '{"reset": true}'                                         # вернуть настоящее время
```

Сдвиг влияет на сроки, просрочку, сумму перерасчёта и доступность шага в ГЖИ.
Свежесть входа проверяется по настоящему времени: иначе перемотка вперёд выбрасывала бы
пользователя с ошибкой «Сессия устарела». Вне демо-режима маршрутов нет.

### Тесты API на настоящей базе

Заявка живёт в нескольких таблицах и транзакциях, поэтому маршруты проверяются не на моках,
а на живой базе. Тесты берут её из `TEST_DATABASE_URL`; если переменная не задана, они
пропускаются, и `pnpm test` проходит без поднятого Postgres.

```bash
docker compose up -d db
docker compose exec db psql -U msc -d postgres -c 'create database msc_test'
TEST_DATABASE_URL=postgres://msc:msc_local_only@localhost:5432/msc_test pnpm --filter @msc/api test
```

Тестовая база очищается перед каждым тестом, миграции применяются автоматически.
Рабочую базу тесты не трогают.

### Мини-приложение без MAX

В браузере нет `window.WebApp`, поэтому в режиме разработки подставляется мок MAX Bridge с тестовым
пользователем — в углу экрана виден бейдж `mock bridge`. Диплинк проверяется параметром в адресе:
`http://localhost:5173/?startapp=r_<id>` открывает экран «У меня тоже».

С `VITE_API_MOCK=1` мини-приложение работает на встроенном моке API с образцовыми заявками и не ходит
в бэкенд. Чтобы работать с настоящим API:

```bash
docker compose up -d db && pnpm --filter @msc/db db:migrate   # база и схема
pnpm --filter @msc/api sign-init-data                          # последняя строка → VITE_DEV_INIT_DATA в .env
# в .env: VITE_API_MOCK=0, CORS_ORIGIN=http://localhost:5173, BOT_TOKEN=dev-token, INIT_DATA_MAX_AGE_SEC=86400
pnpm --filter @msc/api dev
pnpm --filter @msc/miniapp dev
```

Подписанная initData уходит в заголовке `X-Init-Data` как есть, поэтому API принимает мок-пользователя
как настоящего: он создаётся в базе при первом `GET /api/me`.

### API: что уже отвечает

| Метод | Путь | Что |
|---|---|---|
| GET | `/api/health` | проверка живости, текущее время сервера |
| GET | `/api/houses?q=` | поиск дома по адресу, от 3 символов |
| GET | `/api/houses/:id/home` | контакты УК со статусом «открыто до…» по местному времени дома, объявление |
| GET | `/api/houses/:id/categories` | категории заявок для региона дома |
| GET | `/api/me` | кто вошёл: профиль MAX, роль, дом, согласие; первый вызов создаёт пользователя |
| POST | `/api/me/house` | привязка к дому и квартире `{ houseId, apartmentLabel }`, возвращает `/api/me` |
| POST | `/api/photos` | загрузка фото (`multipart`, поле `file`, до 5 МБ, JPEG/PNG/WebP/HEIC); только после входа |
| GET | `/api/photos/*` | отдача загруженного фото |

Маршруты с входом ждут заголовок `X-Init-Data` с подписанной initData из MAX; без него — `401`.
Ошибки всегда в одном формате: `{ "error": { "code": "not_found", "message": "Дом не найден" } }`.

Дома, организации, контакты и категории читаются при старте из `regions/<код>/*.yaml` и `rules/federal/`
(схемы — в `@msc/domain`, происхождение — в `data/README.md`). Дома и организации при старте
переносятся в БД (`apps/api/src/data/seed.ts`), повторный запуск только обновляет строки.

## Запуск в Docker

Весь проект одной командой:

```bash
cp .env.example .env          # если ещё нет; заполнить BOT_TOKEN, USER_HASH_SECRET, USER_ID_ENC_KEY
docker compose up -d --build
docker compose ps -a          # migrate — Exited (0), остальные — Up
```

| Сервис | Что делает | Порт |
|---|---|---|
| `db` | PostgreSQL 16, данные в томе `pgdata` | `127.0.0.1:5432` |
| `migrate` | применяет миграции и завершается | — |
| `api` | HTTP API; при старте загружает дома и УК из `regions/` | 3001, внутри сети |
| `bot` | чат-бот: `BOT_MODE=polling` локально, `webhook` на сервере | 3002, внутри сети |
| `web` | Caddy: мини-приложение, `/api` → api, `/webhook` → bot; HTTPS, если задан `PUBLIC_DOMAIN` | 80, 443 |

`api`, `bot` и `migrate` собираются из корневого `Dockerfile`, `web` — из `apps/miniapp/Dockerfile`.
Порядок запуска: `db` (healthy) → `migrate` (успешно завершилась) → `api`, `bot` → `web`.

```bash
docker compose logs -f api    # логи сервиса (Ctrl+C — выйти)
docker compose stop           # остановить, данные сохраняются
docker compose start          # запустить снова
docker compose down           # удалить контейнеры, тома с данными остаются
docker compose down -v        # удалить всё, включая БД, фото и сертификаты Caddy — осторожно
```

**На сервере** в `.env` дополнительно: `PUBLIC_DOMAIN=<домен>`, `BOT_MODE=webhook`, `WEBHOOK_SECRET`,
собственный `POSTGRES_PASSWORD`.

**Бот с настоящим токеном — только один экземпляр.** Режим polling при старте снимает подписку webhook:
локальный запуск отключит бота на сервере.

### Резервные копии (сервер)

Каждую ночь cron запускает `scripts/backup-db.sh`: копия базы (`db-*.dump`) и фото (`photos-*.tar.gz`)
в `/var/backups/msc`, хранятся 14 дней. Журнал — `/var/log/msc-backup.log`.

```bash
scripts/backup-db.sh                                        # копия прямо сейчас
ls -lh /var/backups/msc                                     # какие копии есть
scripts/restore-db.sh /var/backups/msc/db-ГГГГММДД-ЧЧММ.dump  # восстановить (спросит подтверждение)
```

Копии лежат на том же сервере. Если сервер пропадёт целиком, пропадут и они — время от времени
скачивайте свежую к себе: `scp root@<сервер>:/var/backups/msc/db-*.dump .`

### Мини-приложение как образ

`apps/miniapp/Dockerfile` собирает статику и кладёт её в `caddy:2-alpine` с `apps/miniapp/Caddyfile`:
Caddy отдаёт мини-приложение, проксирует `/api/*` в `api:3001` и `/webhook*` в `bot:3002`.
Сборка — около 20 секунд.

```bash
docker build -f apps/miniapp/Dockerfile -t msc-miniapp .
docker run --rm -p 8080:80 msc-miniapp            # http://localhost:8080 — без TLS
docker run --rm -p 80:80 -p 443:443 -e PUBLIC_DOMAIN=example.ru msc-miniapp   # на сервере: HTTPS сам
```

Переменные `VITE_*` передаются в сборку аргументами: `--build-arg VITE_BOT_NAME=…`.

### Сервер: развёртывание, деплой, откат

Как поднять систему на новом сервере, выкатывать изменения (вручную и автодеплоем), откатываться,
подключать исполнителей и разбирать частые проблемы — в [docs/operations.md](docs/operations.md).

## Правила разработки

- **Ветки** по зонам: `a/…`, `b/…`, `v/…`. В `master` — только через pull request, его смотрит хотя бы один
  другой участник.
- **Договоры** между частями — в `packages/domain/src/contracts`; меняются только PR с одобрением обеих сторон.
- **Зависимости** — только командой `pnpm --filter … add -E`, точные версии, без `^`. `pnpm-lock.yaml`
  коммитится вместе с `package.json`.
- **Стиль** — перед коммитом `pnpm format && pnpm lint`.
- **Секреты** — только в `.env`. В репозитории — `.env.example` без рабочих значений.
- **Бот с настоящим токеном** запускается только у одного человека: второй экземпляр на том же токене
  «перехватывает» часть сообщений. Остальные работают с мини-приложением через мок MAX Bridge.
- **Коммиты** — от своего имени.
- **README** обновляется в том же PR, что и изменение, которое он описывает.

## Проверка решения (для жюри)

**Бот:** [max.ru/t146_hakaton_max_bot](https://max.ru/t146_hakaton_max_bot). Мини-приложение открывается
кнопкой «Мой дом» в меню бота, работает в мобильном и веб-клиенте MAX. На сервере включён демо-режим
(`DEMO_MODE=1`), поэтому весь сценарий проходится **одним аккаунтом**: заявка принимается сразу,
роль диспетчера берётся в профиле, время перематывается «Демо-часами» (плашка в левом верхнем углу).

### Сценарий, 5 минут

| Шаг | Что сделать | Что должно получиться |
|---|---|---|
| 1. Вход и дом | Открыть бота → «Мой дом». В поиске «Где вы живёте?» набрать `Садовая`, выбрать «Казань, ул. Садовая, 12», квартира `48` | Главная: адрес дома в шапке, кнопка «Сообщить о проблеме», УК со статусом «Диспетчер на связи до …», аварийная служба с кнопкой звонка. Регистрации нет: вход по аккаунту MAX |
| 2. Заявка | «Сообщить о проблеме» → «Холодные батареи» → время начала, замер `15` °C, комната, фото по желанию → «Далее: проверить» → «Отправить в УК» | Карточка заявки: статус «Принята», в шапке срок ответа УК по нормативу и сколько осталось. Блок «У меня тоже» с кнопкой «Поделиться в чат дома» |
| 3. «У меня тоже» | «Поделиться в чат дома» (или иконка копирования) и открыть ссылку со второго аккаунта | Второй житель видит суть и подъезд, но не автора; указывает квартиру и замер → «У меня тоже». У автора растёт число квартир. Ссылка вида `https://max.ru/t146_hakaton_max_bot?startapp=r_<id>` |
| 4. Кабинет УК | «Профиль» → «Стать диспетчером» → «Кабинет диспетчера» | Заявки сгруппированы по проблеме: одна строка на дом и причину, число квартир, срок, цена простоя и её рост в час. В группе: назначить исполнителя («Иванов И.» по отоплению) → «Исполнитель приступил» → «Отметить выполненной» с фото |
| 5. Срок и деньги | До шага 4 или вместо него: «Демо-часы» → «+1 день» | У жителя в карточке «Срок вышел», сумма перерасчёта растёт, в «Как посчитано» — расчёт по шагам со ссылками на нормы. У диспетчера группа красная, счётчик «просрочено». Открывается обращение в ГЖИ (PDF). «сброс» возвращает настоящее время |
| 6. Результат | После «Отметить выполненной» открыть заявку жителем: «Всё исправили» или «Вернуть» | Заявка закрыта или возвращена в работу. «Скачать заявление» — PDF заявления о перерасчёте с суммой и расчётом |

Дополнительно: «Профиль» → «Мои данные» — что о пользователе хранится и удаление всего одной кнопкой
с подтверждением. «Сменить дом» — привязка к другому дому, «Назад» возвращает в профиль.

Исполнитель работает в боте: наряд, «Принял», «Выполнено» с фото, «Не могу». Как подключить аккаунт
исполнителя — [docs/operations.md, «Исполнители»](docs/operations.md#исполнители). Без этого шага 4
проходится кнопками в кабинете.

### Проверка без MAX

Тот же сценарий проходится в браузере на встроенных моках MAX Bridge и API, без базы и бота:

```bash
pnpm install
VITE_API_MOCK=1 pnpm --filter @msc/miniapp dev -- --host
# открыть http://localhost:5173
```

В моке уже есть две заявки дома, данные живут до перезагрузки страницы. Диплинки проверяются параметром
в адресе: `?startapp=r_<id>` (присоединиться), `?startapp=req_<id>` (карточка),

под кнопкой будет причина, ссылку можно скопировать иконкой рядом.

Запуск всего проекта в Docker, остановка и повторный запуск — в разделе [Запуск в Docker](#запуск-в-docker).

## Происхождение данных

Требование задания: если вместо реального подключения к внешней системе используются
подготовленные данные, это должно быть явно указано. Таблица ниже — единственное место,
где перечислено происхождение каждого файла. В интерфейсе то же самое показывается бейджем
у каждого значения: `факт` — официальный источник, `модель` — наши данные для MVP.

### Правила — `rules/federal/`

| Файл | Что внутри | Происхождение |
|---|---|---|
| `quality-354.yaml` | Нормы температуры воздуха и горячей воды, допуски день/ночь, проценты снижения платы | Приложение 1 к ПП РФ № 354. **Требует сверки с действующей редакцией перед защитой** |
| `interruption-354.yaml` | Допустимая продолжительность перерывов подачи, пороги, плановое отключение | Там же. Срок планового летнего отключения задаётся санитарными правилами и тоже требует сверки |
| `deadlines-416.yaml` | Сроки, по которым считается `dueAt` | `ads.*` — ПП РФ № 416; `repair.*` помечены `model`: единой федеральной нормы нет, срок устанавливается договором управления |

Правила федеральные и от региона не зависят. Версия файлов (`version`) попадает
в каждый расчёт: по ней расчёт воспроизводится.

### Регион — `regions/16-tatarstan/`

| Файл | Что внутри | Происхождение |
|---|---|---|
| `meta.yaml` | Код, название, часовой пояс, версия правил | модель |
| `categories.yaml` | Категории заявок и ссылки на нормы | модель, набор составлен под сценарий |
| `tariffs.yaml` | Тарифы на отопление, горячую и холодную воду | **модель**, порядок величин реалистичный; заменяются решениями регионального тарифного органа |
| `normatives.yaml` | Нормативы потребления | **модель**, заменяются официальными |
| `orgs.yaml` | УК и ГЖИ с телефонами и графиком | **модель**, вымышленные организации и номера |
| `houses.yaml` | Дома с идентификаторами | **модель**, `fiasId` не настоящие |

### Второй регион — `regions/77-moscow/`

Состав файлов тот же, значения другие: тарифы и нормативы выше казанских, часть сроков
отличается, набор категорий свой — есть мусоропровод, нет детской площадки. Все данные
модельные.

Регион добавлен целиком данными: в движке ничего не менялось. Это проверяется тестом
`packages/domain/src/regions/scaling.test.ts` — он прогоняет один и тот же случай
(шесть часов при +15 °C) на обоих регионах и требует, чтобы часы нарушения совпали,
а суммы разошлись.

Порядок подключения следующего региона:

1. создать каталог `regions/<код>-<название>/` с теми же семью файлами;
2. запустить `pnpm --filter @msc/domain test` — схемы проверят ссылки между файлами;
3. перезапустить API: дома, организации, контакты и исполнители заедут в базу сами.

### Что потребуется для реальных данных

- **Тарифы и нормативы** — решения регионального тарифного органа, публикуются ежегодно.
- **Дома и организации** — ГИС ЖКХ и государственный адресный реестр; нужен доступ к API.
- **Контакты и график** — от управляющей организации при подключении к пилоту.

Код при замене данных не меняется: подключение региона — это добавление каталога
`regions/<код>/`, который проверяется теми же схемами.

## Известные ограничения

- **Модельные данные.** Дома, организации, тарифы и контакты в MVP модельные: это помечено в интерфейсе
  и в [data/README.md](data/README.md).
- **Адрес заявляет сам житель.** Подтверждения по лицевому счёту в MVP нет; косвенно адрес подтверждают
  соседи, присоединившиеся к заявке. В пилоте привязку подтверждает диспетчер УК.
- **Демо-режим для проверки.** При `DEMO_MODE=1` любой вошедший может взять роль диспетчера своей УК и
  перемотать общие демо-часы. Это нужно, чтобы жюри прошло сценарий одним аккаунтом; вне демо-режима этих
  маршрутов нет.
- **Отдельного экрана согласия на обработку данных нет.** Что хранится и как удалить всё — в «Мои данные».
- **Ссылка-приглашение исполнителя** без срока действия, её не публикуют в общих чатах
  (подробнее — [docs/operations.md](docs/operations.md#исполнители)).
- **Время на экране** показывается в часовом поясе устройства; оба подключённых региона живут по Москве,
  для региона в другом поясе это нужно доработать.
- **Мини-приложение только в светлой теме.** MAX Bridge не сообщает тему клиента, тёмная тема —
  в планах по `prefers-color-scheme`.
- **Скачивание PDF внутри MAX** идёт через `downloadFile` и работает только по https;
  в браузере без MAX документ скачивается обычным файлом.
