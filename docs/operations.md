## Из чего состоит система

| Сервис | Что делает | Где данные |
|---|---|---|
| `db` | PostgreSQL 16 | том `pgdata` |
| `migrate` | при каждом запуске применяет миграции и завершается | — |
| `api` | HTTP API мини-приложения | фото — том `photos` (`/data/photos`) |
| `bot` | чат-бот: меню, наряды исполнителям, уведомления, приём фото | тот же том `photos` |
| `web` | Caddy: HTTPS, мини-приложение, `/api` → api, `/webhook` → bot | сертификаты — том `caddy_data` |

Наружу открыты только порты 80 и 443 (Caddy). База слушает `127.0.0.1:5432`, API и бот — только
внутри Docker-сети.

Вне Docker на сервере:

| Что | Где |
|---|---|
| Настройки и секреты | `/opt/max-smart-city/.env` |
| Резервные копии | `/var/backups/msc`, журнал `/var/log/msc-backup.log` |
| Расписание копий | `/etc/cron.d/msc-backup` |
| Автодеплой (если включён) | `/etc/cron.d/msc-deploy`, журнал `/var/log/msc-deploy.log` |

## Развернуть на новом сервере

**Что нужно:** VPS с Ubuntu 22.04+ (от 2 ГБ памяти, от 20 ГБ диска), домен с A-записью на IP сервера,
открытые порты 80 и 443, токен бота MAX.

### 1. Docker

```bash
curl -fsSL https://get.docker.com | sh
docker compose version        # Docker Compose v2
```

### 2. Код

Серверу нужен доступ к репозиторию только на чтение — ключ развёртывания (deploy key):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N ''     # -N '' — ключ без пароля
cat ~/.ssh/github_deploy.pub                             # → GitHub: Settings → Deploy keys, без права записи
cat >> ~/.ssh/config <<'CFG'
Host github.com
  IdentityFile ~/.ssh/github_deploy
  IdentitiesOnly yes
CFG
git clone git@github.com:MrHold/max-smart-city.git /opt/max-smart-city
cd /opt/max-smart-city
```

### 3. Настройки

```bash
cp .env.example .env
nano .env
```

Что поменять относительно примера:

| Переменная | Значение на сервере |
|---|---|
| `POSTGRES_PASSWORD` | свой: `openssl rand -hex 24` |
| `BOT_TOKEN` | токен бота |
| `BOT_MODE` | `webhook` |
| `WEBHOOK_SECRET` | `openssl rand -hex 32` |
| `PUBLIC_DOMAIN` | домен, например `example.ru` — Caddy сам получит сертификат |
| `CORS_ORIGIN` | `https://<домен>` |
| `APP_LINK` | `https://max.ru/<ник бота>` |
| `VITE_BOT_NAME` | ник бота |
| `USER_HASH_SECRET` | `openssl rand -hex 32` — **один раз**, см. ниже |
| `USER_ID_ENC_KEY` | `openssl rand -base64 32` — **один раз**, см. ниже |
| `DEMO_MODE`, `VITE_DEMO_MODE` | `1` на защите, `0` в пилоте |

`DATABASE_URL`, `API_PORT`, `PHOTOS_DIR` в Docker задаются в `compose.yaml` — в `.env` их трогать не нужно.
В сборку мини-приложения из `.env` попадают только `VITE_BOT_NAME` и `VITE_DEMO_MODE`.

### 4. Запуск и проверка

```bash
docker compose up -d --build
docker compose ps -a                                # migrate — Exited (0), остальные — Up
curl -s https://<домен>/api/health                  # {"ok":true,"now":"…"}
docker compose logs bot --since 2m                  # бот стартовал, webhook установлен
```

В настройках бота на платформе MAX адрес мини-приложения должен быть `https://<домен>`.

### 5. Резервные копии и (по желанию) автодеплой

```bash
echo '0 1 * * * root /opt/max-smart-city/scripts/backup-db.sh >> /var/log/msc-backup.log 2>&1' \
  > /etc/cron.d/msc-backup                          # каждую ночь в 01:00 UTC
```

Автодеплой — в разделе [Деплой и откат](#деплой-и-откат).

## Секреты, которые нельзя менять

`USER_HASH_SECRET` и `USER_ID_ENC_KEY` генерируются **один раз** при первом запуске.

- По `USER_HASH_SECRET` пользователь находится в базе. Сменили — все жители, диспетчеры и исполнители
  при следующем входе станут новыми пользователями без домов, заявок и привязок.
- `USER_ID_ENC_KEY` шифрует идентификатор MAX, по которому бот пишет людям. Сменили — уведомления
  и наряды перестают доходить: старые идентификаторы больше не расшифровать.

Копию `.env` храните вне сервера (например, в менеджере паролей). Резервная копия базы без этих двух
ключей бесполезна.

`BOT_TOKEN` и `WEBHOOK_SECRET` менять можно: после правки `.env` выполнить `docker compose up -d`.

## Бот

### Режимы

| Режим | Где | Как работает |
|---|---|---|
| `webhook` | сервер | MAX сам присылает события на `https://<домен>/webhook` с секретом `WEBHOOK_SECRET` |
| `polling` | локально | бот сам спрашивает MAX о новых событиях |

**На один токен — один запущенный бот.** Режим `polling` при старте снимает webhook, и бот на сервере
перестал бы получать сообщения. Поэтому перед стартом в `polling` бот спрашивает MAX, подписан ли токен
на webhook, и если да — не запускается и пишет «Этот токен уже работает на сервере». Обойти можно только
явно: `FORCE_POLLING=1`. Если webhook всё-таки сняли — `docker compose restart bot` на сервере вернёт его.

### Проверить бота локально на настоящем токене

```bash
# на сервере — выключить боевого бота
docker compose stop bot

# у себя — один раз склеить сертификаты Минцифры (без них Node не доверяет MAX: «fetch failed»)
cat docker/certs/*.crt > /tmp/ru-ca.pem

# у себя — BOT_MODE=polling в .env, база поднята и мигрирована
( set -a && . ./.env && set +a && \
  NODE_EXTRA_CA_CERTS=/tmp/ru-ca.pem FORCE_POLLING=1 pnpm --filter @msc/bot exec tsx src/index.ts )
# … проверили, Ctrl+C

# на сервере — вернуть
docker compose start bot
```

- `set -a && . ./.env && set +a` — подгрузить переменные из `.env`: при запуске через `pnpm … exec`
  он сам не читается. Скобки — подоболочка, переменные не остаются в терминале.
- `NODE_EXTRA_CA_CERTS` — без него Node не доверяет сертификату MAX (удостоверяющий центр Минцифры)
  и бот падает с `fetch failed`. В Docker сертификаты уже подложены в образ.
- `FORCE_POLLING=1` — webhook остаётся записанным за токеном и после остановки бота на сервере,
  поэтому без флага локальный бот откажется стартовать. Это защита сервера.

### Что умеет бот

- `/start`, `/help` — приветствие и меню: «Мой дом» (мини-приложение), «Контакты УК», «Что умеет бот».
- Наряды исполнителям и приём фото результата — см. [Исполнители](#исполнители).
- Уведомления жителям и диспетчерам — см. [Уведомления](#уведомления).
- Повторное нажатие той же кнопки в течение 3 секунд игнорируется.

## Исполнители

### Подключить исполнителя

Исполнитель получает наряды в боте, только если привязан к своему аккаунту MAX. В кабинете диспетчера
(«Исполнители») у таких стоит «в MAX», у остальных — «нет в MAX» и кнопка «Пригласить в бот».

1. Диспетчер нажимает «Пригласить в бот» и пересылает ссылку исполнителю.
   Все ссылки сразу можно получить на сервере:
   ```bash
   docker compose exec bot node --import tsx src/dev/invite-links.ts
   ```
2. Исполнитель открывает ссылку в MAX — бот отвечает «Готово, <имя>! Наряды по заявкам будут приходить сюда».

Ссылка-приглашение — это доступ к нарядам: её **не публикуют** в общих чатах. Срока действия у неё пока нет,
и повторное открытие ссылки с другого аккаунта перепривязывает исполнителя (см. [Перед пилотом](#перед-пилотом)).

### Как исполнитель работает в боте

1. Диспетчер назначает заявку — исполнителю приходит **наряд**: номер, адрес, что случилось, описание,
   плановое время. Эта карточка сохраняется в сообщении на каждом шаге.
2. **«Принял»** — заявка «в работе», житель получает уведомление.
3. **«Выполнено»** — открывается приём фото результата.
4. Исполнитель присылает фото (до 5 в одном сообщении, до 10 на заявку, до 5 МБ каждое; JPEG, PNG, WebP).
   Кнопки «✅ Завершить заявку» и «↩️ Назад» всегда под последним сообщением бота.
5. **«Завершить заявку»** — заявка выполнена, житель получает уведомление с числом фото и подтверждает
   результат в мини-приложении, где фото видны в блоке «Результат работы».

**«Не могу»** снимает исполнителя с заявки, диспетчерам дома приходит уведомление. **«Назад»** из приёма фото
возвращает наряд с кнопками. Если про приём фото забыли, он закрывается сам через 6 часов.

Фото хранятся в томе `photos` (`/data/photos` в контейнерах `api` и `bot`), в базе — таблица `photos`:
`stage = before` — фото жителя, `after` — фото исполнителя.

## Уведомления

API не пишет в MAX напрямую: он кладёт уведомление в таблицу `outbox` в той же транзакции, что и изменение
заявки. Бот раз в 5 секунд забирает очередь и отправляет, не больше 25 сообщений в секунду.

- Ошибка отправки — повтор через 30 с, 1 мин, 2 мин… до 1 часа; после 8 попыток — `failed`.
- Человек удалил свои данные — уведомление сразу `failed` с пометкой «адресат удалил свои данные».
- В `last_error` и в логе идентификатор MAX заменён на `***`.

Посмотреть очередь и повторить отправку — в разделе [База данных](#база-данных).

## Вход через MAX

Мини-приложение присылает в каждом запросе `X-Init-Data` — данные запуска, подписанные MAX ключом из
`BOT_TOKEN`. API проверяет подпись и свежесть:

- данные действуют `INIT_DATA_MAX_AGE_SEC` секунд (по умолчанию 3600);
- дата подписи из будущего больше чем на 60 секунд отклоняется;
- перемотка демо-часов на проверку входа не влияет.

При отказе в логе API — строка `initData не прошла проверку` с причиной (саму initData не пишем):

| `reason` | Что значит | Что делать |
|---|---|---|
| `bad_signature` | подпись не сошлась | `BOT_TOKEN` в `.env` не от того бота |
| `expired` | данные устарели или из будущего | закрыть и открыть приложение; проверить часы: `timedatectl` → `synchronized: yes` |
| `malformed`, `no_user` | данные повреждены | открывать приложение из MAX, а не по прямой ссылке в браузере |

### Ограничение частоты

Один пользователь — не больше `RATE_LIMIT_MAX` запросов в минуту (по умолчанию 120), дальше `429`.
Считается по пользователю после входа, до входа — по IP. Реальный IP берётся из заголовка, который
ставит Caddy (доверяем ровно одному прокси). Если перед Caddy появится ещё один прокси или CDN,
настройку `trustProxy` в `apps/api/src/app.ts` нужно поменять. `/api/health` не ограничивается.

## Деплой и откат

### Выкатить вручную

```bash
cd /opt/max-smart-city
git pull
docker compose up -d --build        # пересобирает изменённое, миграции применяются сами
docker compose ps -a
```

### Автодеплой

`scripts/auto-deploy.sh` раз в 2 минуты проверяет `origin/master` и, если появились новые коммиты,
делает `git merge --ff-only` и `docker compose up -d --build`. Если на сервере есть свои коммиты,
скрипт остановится, а не будет сливать ветки сам. Если изменились только `*.md` и `docs/`,
файлы подтягиваются без пересборки и перезапуска.

```bash
# включить
cat > /etc/cron.d/msc-deploy <<'CRON'
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
*/2 * * * * root /opt/max-smart-city/scripts/auto-deploy.sh >> /var/log/msc-deploy.log 2>&1
CRON

# выключить (например, на время проверки жюри или отката)
rm /etc/cron.d/msc-deploy

# что выкатывалось
tail -20 /var/log/msc-deploy.log
```

Пока автодеплой включён, **мерж в `master` = выкатка на прод**: в `master` — только с зелёным CI.

### Проверить ветку на сервере до мержа

```bash
rm -f /etc/cron.d/msc-deploy              # иначе автодеплой вмешается
git fetch origin && git switch <ветка>
docker compose up -d --build
# … проверили
git switch master && git pull && docker compose up -d --build
```

### Откатиться

```bash
rm -f /etc/cron.d/msc-deploy              # иначе автодеплой вернёт master обратно
git log --oneline -10                     # найти последний рабочий коммит
git switch --detach <хеш>                 # --detach — встать на коммит, не на ветку
docker compose up -d --build
```

Вернуться к `master`: `git switch master && docker compose up -d --build`.
Откат кода не откатывает миграции базы: если новая версия меняла схему — сначала восстановить копию базы.

## Логи

Логи каждого сервиса хранятся Docker'ом: до 5 файлов по 50 МБ, старые удаляются сами.

```bash
docker compose logs -f bot                          # в реальном времени (Ctrl+C — выйти)
docker compose logs api --since 30m                 # за последние 30 минут
docker compose logs bot --since 1h | grep -i ошибк  # поиск
```

| Что искать | Где | Значит |
|---|---|---|
| `initData не прошла проверку` | api | отказ во входе, см. [Вход через MAX](#вход-через-max) |
| `outbox #… попытка … не удалась` | bot | уведомление не ушло, будет повтор |
| `Фото от исполнителя не сохранилось` | bot | не скачалось или не записалось фото |
| `Режим фото: не удалось убрать старые кнопки` | bot | MAX не дал изменить старое сообщение — не страшно |
| `Этот токен уже работает на сервере` | bot (локально) | защита сработала: локальный бот не стартовал, сервер цел |
| `MAX не отдал данные бота` | bot | неверный `BOT_TOKEN` или нет связи с MAX; без Docker — нет `NODE_EXTRA_CA_CERTS` |
| `"remoteAddress":"…"` | api | IP клиента; если везде `172.…` — сломалась настройка прокси |

В логах нет initData, подписей ссылок на документы (адреса пишутся без `?…`) и идентификаторов MAX.

## База данных

```bash
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'   # выход — \q
```

Полезные запросы:

```sql
-- неотправленные уведомления
select id, status, attempts, payload->>'type' as type, left(last_error, 80) as error
from outbox where status <> 'sent' order by id desc limit 20;

-- отправить заново
update outbox set status = 'pending', attempts = 0, next_at = now() where id = <id>;

-- фото заявки: before — жителя, after — исполнителя
select r.number, p.stage, p.storage_key
from photos p join requests r on r.id = p.request_id
where r.number = '<номер>';
```

### Резервные копии

Каждую ночь cron запускает `scripts/backup-db.sh`: копия базы (`db-*.dump`) и фото (`photos-*.tar.gz`)
в `/var/backups/msc`, хранятся 14 дней. Журнал — `/var/log/msc-backup.log`.

```bash
scripts/backup-db.sh                                        # копия прямо сейчас
ls -lh /var/backups/msc                                     # какие копии есть
tail -3 /var/log/msc-backup.log                             # сделана ли ночная копия
scripts/restore-db.sh /var/backups/msc/db-ГГГГММДД-ЧЧММ.dump  # восстановить (спросит подтверждение)
```

Копии лежат на том же сервере. Если сервер пропадёт целиком, пропадут и они — время от времени
скачивайте свежую к себе: `scp root@<сервер>:/var/backups/msc/db-*.dump .`

## Частые проблемы

| Симптом | Проверить | Решение |
|---|---|---|
| Бот не отвечает | `docker compose ps`, `docker compose logs bot --since 10m` | кто-то запускал бота локально → `docker compose restart bot` |
| Локальный бот: «Этот токен уже работает на сервере» | — | так задумано; для проверки на боевом токене — [Проверить бота локально](#проверить-бота-локально-на-настоящем-токене) |
| Локальный бот: `fetch failed` | — | `NODE_EXTRA_CA_CERTS=/tmp/ru-ca.pem`, см. там же |
| «Не удалось подтвердить вход через MAX» | лог api, `reason` | см. [Вход через MAX](#вход-через-max) |
| Уведомления не приходят | очередь `outbox`, `last_error` | бот запущен? см. [Уведомления](#уведомления) |
| Исполнителю не приходят наряды | в кабинете у него «нет в MAX» | отправить ссылку-приглашение |
| Житель не видит фото исполнителя | таблица `photos`, есть ли `after` | нет — лог бота; есть — обновить мини-приложение |
| Нет HTTPS | `docker compose logs web` | A-запись домена, открыты 80/443, `PUBLIC_DOMAIN` в `.env` |
| `429 Слишком много запросов` | — | поднять `RATE_LIMIT_MAX`, `docker compose up -d` |
| Кончилось место | `df -h`, `docker system df` | `docker image prune -f`, удалить старые копии из `/var/backups/msc` |

## Правила, которые нельзя нарушать

- **Никогда `docker compose down -v` на сервере** — удалит базу, фото и сертификаты. Сертификаты Let's Encrypt
  выдаются с лимитом: частые пересоздания заблокируют выпуск на неделю.
- `USER_HASH_SECRET` и `USER_ID_ENC_KEY` не менять и хранить копию вне сервера.
- На один токен бота — один запущенный экземпляр.
- Секреты — только в `.env`: не в git, не в чатах, не на скриншотах.
- Ссылки-приглашения исполнителей не публиковать.
- В `master` — только через pull request с зелёным CI.

## Перед пилотом

Для защиты включены демо-упрощения. Для работы с настоящими домами:

- [ ] `DEMO_MODE=0` и `VITE_DEMO_MODE=0`, пересобрать: `docker compose up -d --build` — выключает перемотку
      времени и роль диспетчера одним аккаунтом.
- [ ] Удалить членства диспетчеров, созданные в демо-режиме (`memberships`, `role = 'dispatcher'`);
      оставить только выданные управляющей организацией.
- [ ] Очистить базу от тестовых заявок (после резервной копии).
- [ ] Срок действия у ссылок-приглашений исполнителей и уведомление диспетчеру при перепривязке.
- [ ] `CORS_ORIGIN` — строго боевой домен.
- [ ] Заголовки безопасности и лимит размера запроса в `apps/miniapp/Caddyfile`.
- [ ] Каждому сервису — только его переменные окружения вместо общего `.env`.
- [ ] Действия в CI закрепить по хешу коммита, а не по тегу.
- [ ] Ночная чистка фото без заявки (загружены, но заявку не отправили) старше суток.
- [ ] Суточная квота на загрузку фото одним пользователем.
- [ ] Резервные копии — ещё и вне сервера (другой сервер или облачное хранилище), автоматически.
- [ ] Мониторинг: внешняя проверка `https://<домен>/api/health` с оповещением.
